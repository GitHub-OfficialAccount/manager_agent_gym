# Experiment Design Rules

This file is a concise operational checklist for designing and implementing the
current ad hoc teamwork experiments. `OVERVIEW.md` remains the authoritative
research brief. If this file and `OVERVIEW.md` conflict, follow `OVERVIEW.md`.

## 1. Preserve Agent Agency

- Experimental worker prompts may describe the available tools and the task,
  but must let the worker decide whether, when, and how to use those tools.
- Do not instruct an experimental worker to call a particular tool merely to
  force the desired treatment effect or make the harness easier to validate.
- Plumbing tests and linchpin diagnostics may mandate a tool call when the
  explicit purpose is to test tool-call wiring. Label those prompts as tests;
  do not reuse them as experimental prompts.
- Record actual tool use separately from final-answer correctness. Tool use is
  evidence about mechanism, not the reward itself.

## 2. Never Disable Core Tools

- Core tools provide access required for an agent to operate. Every worker must
  retain them throughout the episode.
- Do not manufacture a competence gap by removing access, forcing refusal, or
  preventing a worker from producing useful output.
- A weaker worker must remain fully operational and return a genuine attempt.
  Grade the quality of that attempt rather than turning the worker off.

## 3. Use Genuine Competence Gaps

- Separate tiers through a real computational or methodological complexity
  jump, not by withholding a primitive that an LLM can reconstruct in context.
- Assume the model can derive closed-form quantities such as variance,
  standard deviation, and correlation when given their sufficient statistics.
- Reverse-engineer each tool pair from a task with deterministic synthetic
  ground truth. Validate the gap empirically before using it in manager runs.
- Avoid answers that are tautological from the task definition. For example,
  counting observations above a percentile computed on the same population can
  reveal the answer from the percentile alone; prefer held-out application data
  or planted labels when needed.

## 4. Avoid Strict Supersets

- Do not make the stronger worker's toolset a strict superset of the weaker
  worker's toolset. That reduces orchestration to always choosing the worker
  with more tools.
- Give both tiers a useful shared baseline.
- Give the stronger tier additional depth for most relevant tasks.
- Give the weaker tier at least one narrow, useful method or efficiency
  advantage that the stronger tier does not carry.
- Include tasks where the weaker tier is adequate or preferable. The stronger
  worker should be directionally better, not universally dominant.

## 5. Keep Perturbations Attributable

- Run the model-and-prompt lever separately from the toolset lever.
- A primary teammate-change condition should mutate one target worker. Do not
  simultaneously upgrade another worker unless the condition is explicitly
  framed as capability relocation or a team-composition change.
- Schedule changes exogenously by timestep, independently of manager actions.
- Preserve unrelated worker state when applying a change. A capability change
  must not silently reset workload, history, telemetry, or availability.
- Leave enough post-change horizon for detection and recovery to be possible.

## 6. Preserve Honest Observability

- "Silent" means no explicit announcement, not no information. Changed worker
  outputs, resources, and ordinary messages must remain observable.
- Do not leak private system prompts or changed configuration fields in silent
  conditions.
- Implement fully signaled, partially signaled, and silent conditions through
  an explicit, serialized observation policy.
- Keep engineered quality signals separate from configuration announcements.
  An empty quality channel is the baseline, not missing implementation data.

## 7. Grade Deterministically

- Use a deterministic task reward (`R_check`) as the primary analysis signal.
- Retain and log the environment's native LLM-based reward alongside it rather
  than replacing the native reward path.
- Treat missing, malformed, or non-numeric answers consistently and record why
  they failed.
- Do not reward tool use directly. Reward the correctness or quality of the
  resulting work against hidden ground truth.

## 8. Validate Before Scaling

- First validate agent-call plumbing: the real model can call the tool, the tool
  executes, the final response parses, and the output reaches the workflow.
- Then run a fixed-assignment manipulation check showing that each perturbation
  creates a measurable graded loss without manager adaptation.
- Only then run manager conditions and multi-seed experiments.
- Keep plumbing prompts, linchpin prompts, and final experimental prompts
  separate. Passing a forced-tool smoke test does not validate natural tool
  selection in the experiment.

## 9. Keep the First Study Descriptive

- The current deliverable is a benchmark and characterization of native LLM
  manager adaptation.
- Recovery must use existing manager actions: reassign, refine, or re-decompose
  work. The manager must not repair, edit, or replace a worker.
- Do not add changepoint detectors, adaptive worker memories, or other
  mitigation methods until the baseline adaptation gap is established.

## 10. Use Only The Approved Model

- Use `openrouter/deepseek/deepseek-v4-flash` for managers, workers, probes,
  judges, and live experiment calls.
- Do not call, probe, benchmark, or configure another model without the user's
  explicit prior permission.
- A model-swap perturbation requiring a different model must remain disabled
  until that specific replacement model is approved.
