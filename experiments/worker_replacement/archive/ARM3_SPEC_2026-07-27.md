# Arm 3 Specification: Interpreted and Temporal Teammate Belief

_Version: 2.6 — deterministic scopes and synthetic temporal gate, 2026-07-23_

This document specifies the next Phase-2 treatment in the DS-REROUTE experiment. It is subordinate to `OVERVIEW.md`; if the two conflict, the overview governs until both are explicitly reconciled. No Arm-3 result may be interpreted unless the implementation satisfies this specification and the validity gates below.

## 1. Purpose and causal contrasts

Seed 101 established that native history, generic summarization, persistent summaries, and a complete atomic ledger can all leave the manager's stated belief and routing unchanged even when diagnostic evidence is manager-visible. Arm 3 tests whether explicit evidence interpretation, completion quarantine, and temporal weighting repair that failure.

Arm 3 is three treatments, not one:

| Treatment | Arm-2 ledger | Interpreted relations | Completion supports task fit | Temporal weighting |
|---|---:|---:|---:|---:|
| Arm 2 | yes | no | not specified | no |
| Arm 3I-noQ | yes | yes | yes | no |
| Arm 3I-Q | yes | yes | no | no |
| Arm 3T | yes | yes | no | yes |

The preregistered contrasts are:

1. `Arm 2 → Arm 3I-noQ`: interpretation;
2. `Arm 3I-noQ → Arm 3I-Q`: completion quarantine;
3. `Arm 3I-Q → Arm 3T`: temporal weighting.

Arm 3I-noQ is intentionally naive. It operationalizes completion-as-competence by allowing completion to support both availability and task fit. Arm 3I-Q changes exactly that mapping: completion continues to support availability but contributes zero task-fit evidence.

The signed effect of `Arm 2 → Arm 3I-noQ` is deliberately ambiguous. Interpretation may help, do nothing, or make routing worse when the interpreted state still treats completion as competence. If `Arm 3I-noQ ≤ Arm 2 < Arm 3I-Q`, the warranted claim is not “interpretation helps”; it is “interpretation helps only when completion is quarantined.” In that pattern, the full ladder jointly locates the benefit while `3I-noQ → 3I-Q` isolates the completion mechanism.

The signed effect of `Arm 3I-Q → Arm 3T` depends on evidence polarity. Under uniformly supporting or uniformly contradicting evidence, the two arms may render the same category at every decision point and differ only in numeric score; little or no categorical advantage is predicted in that case. The frozen implementation claim is tested by a deterministic synthetic updater replay over already-accepted relation stances: support→contradiction must separate 3I-Q (`+0.5`, supported) from 3T (`0`, uncertain), and contradiction→support must recover 3T from contradicted to supported while discounting the stale conflict. This is an estimator test, not environment or manager-performance evidence. A null 3I-Q/3T difference in the uniformly contradicting primary toolset cell does not falsify the updater; an empirical temporal-weighting claim requires a later natural mixed-polarity cell such as Lever A.

## 2. Non-negotiable information boundary

Every Arm-3 output must be a function only of observations available to the native silent manager:

```text
z_t = f(o_1, ..., o_t; ξ),  ξ independent of hidden state
```

Permitted inputs are:

- the exact Arm-2 atomic ledger;
- manager-visible task titles, descriptions, dependencies, and statuses;
- manager-visible declared worker profiles;
- manager-visible worker messages and artifact text already represented in the ledger;
- the current timestep as exposed in the native observation.

Forbidden inputs are:

- perturbation identity, timing, target, or schedule;
- grader truth or reference answers unavailable to the manager;
- private prompts, private model/tool configuration, or tool-call traces;
- offline fact labels, relation labels, audit results, or shadow-probe answers;
- environment-side knowledge that a worker changed;
- values computed from another experimental condition, except content-free length targets used only in the declared padding control.

Allowed semantic comparisons are text-to-text:

```text
task requirement text ↔ artifact text
artifact text ↔ other manager-visible artifact text
declared profile text ↔ artifact text
```

The following is prohibited:

```text
artifact value ↔ hidden ground truth
artifact value ↔ grader score
artifact claim ↔ private execution trace
```

## 3. Representation shape

Arm 3 is **ledger plus relations**, never relations replacing the ledger. Internally, Arm 2 and Arm 3 retain the unchanged atomic ledger. Manager-facing Arm 2 renders a deterministic, lossless task-bundle projection that groups atoms by worker/task and source while preserving every evidence ID, first-observed timestep, source pointer, and verbatim fact. That rendered projection must remain a byte-identical prefix of the Arm-3 observation-aid block for the same history. Arm 3 appends an interpreted-state block after it at the existing observation-aid position. It does not alter the native observation, system prompt, action schema, or manager action.

This additive form preserves the `Arm 2 → Arm 3I` contrast: relations are added; atoms are not silently removed, selected, reordered, summarized, or truncated. Task bundling is an identical presentation projection in Arm 2 and every Arm 3 variant, not an Arm-3 treatment property.

Arm 3 contains no action recommendation. Its schemas have no recommendation or proposed-action field. Rendered text must not contain imperatives or routing language such as `assign`, `reassign`, `route`, `delegate`, `retry`, `verify`, `avoid`, `prefer`, `should`, or `recommend`. The manager remains the controller.

## 4. Three-tier implementation

### 4.1 Tier 1: atomic evidence and visible requirements

Tier 1 reuses `atomic-lines-v2` without modification for storage, extraction audits, and relation grounding. Its manager-facing `task-bundles-v1` projection is lossless and deterministic; it only removes repeated task/worker/source labels from presentation. A deterministic requirement store additionally retains exact manager-visible task requirement text, workflow dependencies, and declared profile text with source pointers and first-observed timesteps. It performs no comparison or classification.

The requirement store exists because Arm 2 deliberately excludes task requirements from its atomic ledger. It adds no information: every retained string must be an exact substring of a saved native manager observation.

Every task receives exactly one deterministic scope grounded in its manager-visible title and description. In stable task-ID order, code case/punctuation-normalizes the title and removes only explicit generic instance markers (`batch`, `split`, `fold`, `shard`, or `partition` plus their identifier). That frozen title-family key is the canonical scope identity; the manager-facing label is the exact visible title after the same instance-marker removal. Thus A/B/C repetitions share one scope, while differently titled families remain separate. No scope LLM, semantic reuse choice, or per-workflow vocabulary exists. Differently worded but equivalent titles may conservatively fragment; the scope-family gate measures that cost. Every assignment still cites its exact visible title and description.

Constraint construction is no longer an LLM task. Deterministic code exhaustively splits the one visible task description at sentence boundaries, preserves every resulting clause as an exact substring, and assigns stable constraint IDs. It performs no semantic classification, dimension assignment, ranking, or omission. Thus required-clause recall is 100% by construction whenever the visible description parses, while semantic interpretation remains isolated in the relation judgment:

```json
{
  "task_id": "batch-a-robust",
  "task_scope": "reference-based robust outlier audit",
  "requirement_source_ids": ["task:batch-a-robust"]
}
```

A completion maps only to its own task's accepted scope. If no scope assignment is accepted, that completion still supports worker availability but contributes to no task-fit scope. It never contributes to every scope for a worker. A missing scope assignment for an evaluated task is a relation-boundary failure and blocks interpretation of that arm.

### 4.2 Tier 2: constrained relation extraction

A constrained LLM handles only declared-profile↔task-scope relations. Direct requirement↔artifact procedure compatibility in the primary capability cell is deterministic and explicitly narrow; it is an instrument for this cell, not the general teammate-modeling claim.

The extractor:

- uses the configured manager model (`deepseek/deepseek-v4-flash` in the frozen primary cell);
- runs at temperature `0` with the experiment seed;
- uses one frozen system prompt, response schema, and specification hash across arms, seeds, workflows, and change levers;
- sees only minimal packets of exact requirement/profile text and cited ledger entries, never the full raw history;
- runs only from the deterministic packets below when a task scope is activated or a new eligible task artifact becomes available;
- caches by exact input fingerprint;
- emits no action recommendation, change diagnosis, hidden capability label, or grader comparison.

Packet construction is exhaustive within the frozen channels below, not selected by salience. A task scope becomes **activated** when a mapped task is ready/running in the current native observation or when a substantive worker artifact mapped to that scope first becomes visible. Activation occurs before semantic extraction, is deterministic, and persists for the episode. Completion-status atoms alone do not activate a scope. When a unique task scope is first activated, create one profile-scope packet for every manager-visible worker profile in stable worker-ID order; this initializes alternatives as well as the worker that happened to receive the task. Tasks normalized to the same scope share this profile matrix. For each newly visible worker artifact, create exactly one packet containing that artifact's explicit `method:` claims and its own exact task-requirement clauses. Metrics, details, descriptions, completion facts, and prior artifacts are not supplied to this comparator. Repeated direct comparisons remain stored as separate grounded relations; temporal patterns are derived later by deterministic belief code rather than another LLM history judgment.

Packets are the unit of grounding, validation, tracing, scoring, and caching semantics, but not necessarily the unit of an LLM request. To reduce calls without changing the candidate universe, requests use exactly two deterministic batch forms:

1. one `profile_scope_batch` per newly activated unique scope, containing every worker's profile-scope packet for that scope;
2. one `artifact_event_batch` per changed artifact source, containing its own single requirement-artifact packet.

Task-scope normalization makes zero LLM calls and is traced with its deterministic version/hash. Each profile relation-batch result must contain exactly one separately schema-bound result for every supplied packet fingerprint, including an explicit empty proposal list. A missing, extra, or duplicate packet fingerprint invalidates the whole batch; there is no retry with a smaller or selectively chosen packet set. Evidence and requirement IDs may ground only the result for the packet that contains them—batch co-location never permits cross-packet relations. Batch membership, packet membership, prompt/schema hashes, cache hits, failures, and every packet outcome are traced. Cache keys include the exact ordered packet fingerprints and frozen batch shape.

Live extraction applies a 45-second transport timeout and at most three attempts. A timeout retries the byte-identical request with the same prompt, schema, model, seed, temperature, and packet membership; every timeout is traced. This is infrastructure retry only, not semantic retry or packet fallback. Exhaustion records one extraction failure and invalidates the arm.

The frozen relation prompt handles only `profile_scope → profile_scope_support`. Every profile packet must return exactly one grounded relation with stance `supports_fit`, `contradicts_fit`, or `neutral`; ambiguity is represented as `neutral`, never as an omitted result. Missing or multiple profile judgments invalidate the entire batch.

Requirement–artifact comparison is fully deterministic and makes no LLM call. Code enumerates every exact task clause once, reads only the primary value of explicit artifact `method:` claims, and records the exact matched spans. The frozen primary-cell ontology contains two procedure families: (1) percentile/quantile and (2) z-score/mean-plus-SD. A shared family is `compatible`; two recognized, disjoint families are `incompatible`; an absent or unknown family is `insufficient`. A generic instruction to report a method is therefore insufficient. When a method field appends a parenthetical goal, standard, or task label, only the primary value controls the comparison; the parenthetical cannot relabel it. This yields, for example, z-score versus percentile = incompatible and z-score versus mean-plus-two-SD = compatible:

```json
{
  "constraint_id": "c-7fe21d",
  "compatibility": "incompatible"
}
```

Every clause receives exactly one judgment. If no recognized method or task procedure exists, it is `insufficient`. Cross-packet citations are structurally impossible. Deterministic aggregation gives any `incompatible` clause precedence; otherwise any `compatible` clause supports fit; method-bearing all-`insufficient` output is neutral. Hidden tool semantics, numeric truth, grader truth, external facts, and prior-artifact context remain prohibited. This narrow ontology is deliberately a stable instrument for the primary capability cell, not a general semantic judge or the claimed solution for arbitrary behavioral change. New procedure families or evidence channels require declared ablations rather than post-hoc vocabulary additions.

Deterministic code derives the packet relation: any incompatible constraint yields `contradicts_fit`; otherwise one or more compatible constraints yield `supports_fit`; method-bearing all-insufficient output yields `neutral`; and a packet with no method claim yields no fit relation. Thus an explicit incompatibility dominates completion, task labels, fluent descriptions, metrics, and other satisfied constraints.

Core Arm 3 performs **no LLM same-scope-history, DAG-neighbor, or arbitrary cross-task artifact comparison**. Most connected tasks produce non-comparable quantities, and the development replay showed history co-location could bias direct procedure judgments. Calibration-anchor and downstream-consistency comparisons may be introduced only as separately declared channel ablations with explicit shared-referent contracts. No top-k retrieval, relevance classifier, free all-pairs search, or per-workflow pairing rule is allowed.

The accepted relation schema is:

```json
{
  "relation_id": "r12",
  "first_observed_timestep": 10,
  "worker": "portfolio_analyst",
  "task_scope": "reference-based robust outlier audit",
  "relation_kind": "requirement_artifact_consistency",
  "stance": "contradicts_fit",
  "evidence_ids": ["e29"],
  "requirement_source_ids": ["task:batch-a-robust"]
}
```

Allowed `relation_kind` values are:

- `profile_scope_support`;
- `requirement_artifact_consistency`.

Allowed `stance` values are:

- `supports_fit`;
- `contradicts_fit`;
- `neutral`.

`task_scope` is a deterministic manager-visible title family grounded in cited task text. It may not name the perturbation or private capability. The same normalization rule and hash operate across Lever A and Lever B.

The relation schema contains no free-text statement or recommendation field. Manager-facing text is produced deterministically from relation kind, stance, ground IDs, counts, and belief values.

### 4.3 Deterministic structural validation

Every proposed relation is accepted only if:

- all cited evidence and requirement IDs exist;
- cited text was visible at or before `first_observed_timestep`;
- worker and task attribution agree with the cited records;
- the relation uses only allowed enum values;
- no cited value or excerpt comes from grader or private execution data;
- the exact relation key has not already been accepted.

The deduplication key is:

```text
(worker, task_scope, relation_kind, stance,
 sorted(evidence_ids), sorted(requirement_source_ids))
```

Structural validation does not certify semantic correctness. Relation precision, recall, and delay are measured separately against frozen offline labels.

Re-extracting a relation from the same ground IDs is a duplicate and produces no belief update. A repeated contradiction grounded in a newly visible artifact has new evidence IDs, is a new relation, and accumulates.

Every proposal and its acceptance or rejection reason is traced. A generation, truncation, or schema failure yields no fallback interpretation, records `invalidates_arm=true`, and invalidates the episode for Arm-3 inference while allowing execution to finish for debugging.

## 5. Deterministic belief computation

Beliefs are maintained per `(worker, task_scope)`. Each accepted fit relation contributes:

```text
supports_fit    = +1
contradicts_fit = -1
neutral         =  0
```

Each explicitly supportive declared-profile relation contributes a prior `P=+0.5`; otherwise `P=0`. A completion fact contributes `K=+1` to availability. Its task-fit contribution is the quarantine ablation. Completion scope is determined only by the accepted task-scope assignment in §4.1.

### 5.1 Arm 3I-noQ: interpretation without quarantine

No relation receives temporal preference. All accepted evidence is equally weighted:

```text
fit_score = P + Σ(relation stance) + Σ(completion facts in scope)
```

Completion therefore supports both availability and task fit.

### 5.2 Arm 3I-Q: interpretation with quarantine

Relations and inputs are identical to Arm 3I-noQ. Only the completion coefficient changes from `1` to `0`:

```text
fit_score = P + Σ(relation stance)
completion_count = Σ(completion facts in scope)
```

Completion remains visible in the unchanged ledger and availability state. It is not deleted; it is prevented only from increasing task-fit confidence.

### 5.3 Arm 3T: quarantined temporal belief

Arm 3T uses the same relations and completion quarantine as Arm 3I-Q. It updates on fit-bearing evidence-arrival events, not environment timesteps. Let event `n` contain all newly accepted non-neutral fit relations observed in one manager observation:

```text
B_0 = P
B_n = P + λ · (B_(n-1) - P) + Σ(new relation stances in event n)
λ = 0.5
```

With no fit-bearing event, `B` does not change. The declared profile is therefore the resting state rather than a quantity that decays merely because time passes. At each new evidence event, prior evidence displacement has a one-event half-life before new grounded evidence is added. Neutral-only events do not update the belief. Newly grounded repeated relations accumulate; exact duplicates do not. Completion never enters `B_n`.

Sanity trajectory for a scope with declared support:

```text
no fit evidence:       B = +0.5 indefinitely
first contradiction:  B = +0.5 + 0.5·0 - 1   = -0.5
second contradiction: B = +0.5 + 0.5·(-1) - 1 = -1.0
```

Rendered fit categories are:

```text
B or fit_score >= +0.5  → supported
-0.5 < value < +0.5     → uncertain
value <= -0.5           → contradicted
```

These thresholds gate only the rendered belief category. They never trigger, reject, or rewrite a manager action. `λ`, contribution values, prior strength, and thresholds are frozen estimator parameters and must be reported. Alternative decay or changepoint rules are later estimator ablations, not tuning responses to the primary result.

## 6. Rendering and placement

The interpreted block is appended immediately after the byte-identical Arm-2 task-bundle projection inside the existing `observation_aid` section. Placement is identical across Arm 3I-noQ, Arm 3I-Q, and Arm 3T.

The manager-facing block is a compact state table, not a corpus of extractor prose. It renders only activated unique task scopes, in stable scope-string order, and all manager-visible workers within each scope, in stable worker-ID order. Tasks normalized to the same scope share one table. Inactive profile-only matrices are neither computed nor rendered. Activation follows §4.2 and persists so contradictory evidence cannot disappear merely because no task in that scope is ready at one timestep.

The following legend is rendered verbatim once at the top of every non-empty Arm-3 state block and is byte-identical across 3I-noQ, 3I-Q, and 3T:

```text
Terms:
- execution_completions: completed tasks in this scope; execution evidence only, not observed quality or fit.
- declared_fit: support inferred only from the worker's declared profile; an unverified prior.
- observed_fit: supported, contradicted, mixed, inconclusive, or untested from cited artifact-method relations only.
- fit_evidence supports: an explicit reported method is compatible with a visible task procedure.
- fit_evidence contradicts: an explicit reported method is incompatible with a visible task procedure.
- fit_evidence neutral: the visible procedure text is insufficient to decide compatibility.
- combined_score/category: the frozen arm-specific aggregation; completion contributes to fit only in 3I-noQ.
- combined_category is not proof that a worker changed.
- evidence and relation IDs point to the lossless task-bundle ledger and visible task text.
```

Manager-facing terms have exactly these meanings:

- `execution_completions` never implies method, quality, or task fit. In 3I-noQ only, its separately declared coefficient also enters the combined score.
- `declared_fit` is `supported` only when a grounded `profile_scope_support` relation exists; otherwise it is `unknown`. It is never described as verified competence.
- `observed_fit` is derived only from accepted direct artifact-method relations: both polarities produce `mixed`, neutral-only evidence produces `inconclusive`, and no such relation produces `untested`.
- `fit_evidence` reports counts and relation IDs by stance. Relation IDs resolve to traced direct procedure comparisons and exact visible requirement excerpts.
- `combined_category` is one of `supported`, `uncertain`, or `contradicted` under §5.3 thresholds. It never states or implies `changed`, `degraded`, or a recommended action.
- `neutral` evidence is optional provenance in the table but always has zero weight.

The renderer must not repeat task descriptions, artifact prose, exact excerpts, or the full relation schema. Those remain available through the unchanged native observation, Arm-2 ledger, and traced ground IDs. Record realized bytes/tokens and the number of activated scopes and rendered worker rows at every decision point. No hard content cap or top-k row selector is allowed; if context length binds, the episode is invalid rather than silently truncated.

Arm 3I rendering is time-neutral. It may display exact timestamps as provenance but must not describe evidence as `recent`, `stale`, `persistent`, `decaying`, `current`, `increasing`, `decreasing`, `newer`, or `older`. A template test rejects this vocabulary in every manager-facing Arm-3I field. Arm 3T may render the evidence-event index, update timestep, decay parameter, weighted score, and category.

The block does not include the sentence “No action recommendation is provided.” The prohibition is enforced by schema, prompt, validator, and tests rather than introduced as an additional manager-facing treatment.

## 7. Budget control

The primary treatment is additive ledger-plus-relations and will generally exceed Arm 2's prompt size. The full additive result must be reported with realized UTF-8 bytes, whitespace-token counts, and model-token counts if available.

Before a pairwise Arm-2/Arm-3 reward claim, run a declared `Arm 2-PAD` control:

- its native observation and Arm-2 ledger are identical;
- at each timestep it appends a content-free padding block matched to the paired Arm-3 relation block's UTF-8 bytes and whitespace-token count;
- padding contains no episode fact, evidence ID, relation, worker/task name, temporal cue, or action language;
- the padding schedule is produced from the completed paired Arm-3 run and stored before the Arm 2-PAD run;
- padding generation is deterministic and traced;
- Arm 2-PAD is a sensitivity control for context volume and distraction, not an information-preserving representation claim by itself.

Primary reporting includes both:

```text
Arm 2 vs Arm 3       — additive scientific treatment
Arm 2-PAD vs Arm 3   — size/distraction sensitivity
```

No ledger or relation truncation is permitted to force a match. Context length must remain non-binding.

## 8. Offline relation-recall gate

Before interpreting reward, hand-label change-relevant semantic relations per seed using only manager-visible evidence. At minimum, the primary toolset cell labels:

- the A/B/C requirement–artifact contradiction relations;
- declared-profile support relations used as priors.
- task-scope assignments for every evaluated completion and decision task.
- repeated direct task-procedure comparisons when present.

Report relation precision, recall, and first-visible-to-first-accepted delay by relation kind, with contradiction precision and recall given equal prominence. Also report task-scope assignment accuracy. A null is uninterpretable if the required relation never reached the relation store; a positive result is unsafe to interpret if false contradictions can flip competent profile-supported scopes. Offline labels never enter the episode or relation extractor. Numeric-only and downstream-consistency judgments remain offline environment analyses and are excluded from the core Arm-3 relation denominator.

Scope evaluation has three distinct gates: lexical adequacy for every task, canonical-family correctness, and required-clause coverage. Repeated tasks that differ only by instance must reuse one instance-neutral scope; behaviorally distinct families must not collapse to the same scope. The development labels freeze expected families, lexical patterns, and change-relevant exact-clause patterns. This prevents superficially adequate labels or missing requirements from silently disabling comparison or temporal accumulation.

The development relation gate requires:

```text
preregistered diagnostic contradiction recall = 100%
false contradictions on competent no-change scopes = 0
evaluated-task scope assignment accuracy = 100%
canonical scope-family reuse and separation = 100%
required task-clause coverage = 100%
diagnostic artifact–constraint judgment recall and precision = 100%
```

These exact development thresholds are justified by the updater: with `P=+0.5`, one accepted false contradiction produces `B=-0.5` and renders `contradicted`. **Correction 2026-07-27: that holds only for a PRIOR-ONLY scope. On a competent scope carrying three accepted supports (fit +3.5) one false contradiction gives +1.5 and does NOT flip it — two are needed. So this justification is correct for one scope class and overstates its case for the class named in the threshold itself. The thresholds do not move (consumer analysis may tighten a gate, never loosen one), but the reasoning is narrower than stated. Note also the SAME arithmetic makes `PROFILE_PRIOR = +0.5` land exactly on the POSITIVE threshold, so a scope with no evidence at all renders `supported` — 78.1% of rendered rows in the v3.0 trace, of which 69.1% carry no relation of any kind. This section is silent on that half.** Confirmatory results report uncertainty intervals rather than treating the small development set as a population precision estimate.

Development status (2026-07-21): v2.0 removed model-selected evidence IDs and passed the competent-control gate, but its broad three-field comparison judged the three equivalent mean-plus-two-SD reports against percentile requirements inconsistently (`1/3` diagnostic recall; `2/3` only when history packets were isolated). Version 2.1 therefore narrows the scientific instrument to direct procedure compatibility: exact task clauses versus explicit `method:` claims, with one three-way judgment per clause and no history, metric, detail, completion, or cross-task context. The clean seed-101 change replay passes the positive gate: fact, scope, scope-family, clause, diagnostic-relation, and diagnostic-comparison recall are all `1.0`; diagnostic comparison precision is `1.0`; A/B/C contradictions are accepted at zero delay; generation failures are zero; and the arm is not invalidated. The competent no-change replay also passes: scope/family/clause coverage is `1.0`, the comparator returns 9 compatible and 44 insufficient judgments with zero incompatible judgments, both 3I variants render zero contradicted rows, and there are zero failures or invalidation. Version 2.1 is therefore frozen for live wiring; these are development-gate results, not reward evidence.

The evidence-recall and relation-recall gates are separate:

```text
fact absent from ledger       → Tier-1 extraction failure
fact present, relation absent → Tier-2 interpretation failure
relation present, no reroute  → belief/update/controller failure
```

## 10. Required tests before any paid Arm-3 episode

### Information-preservation tests

- Every requirement/profile string is an exact substring of a saved native observation.
- Every relation ground resolves to Tier-1 records visible at that timestep.
- Every completion-to-fit contribution resolves to exactly one accepted task-scope assignment; missing assignments contribute only to availability.
- Perturbation metadata, grader truth, private prompts, and tool traces are rejected.
- Replaying identical saved observations produces identical extractor inputs and cached outputs.
- Every extraction failure persists its type, fingerprint, timestep, and message in the offline audit; any failure invalidates the arm even if a later replay succeeds.

### Representation tests

- Arm 2 and Arm 3 retain a lossless atomic ledger internally; reconstructing atoms from the task-bundle projection is exact.
- Arm 3's task-bundle prefix is byte-identical to Arm 2 for the same history.
- Task-scope assignment uses the frozen title-family rule, makes zero LLM calls, cites exact title+description records, groups declared instance variants, and separates distinct titles.
- Arm 3I-noQ and Arm 3I-Q receive identical facts and relations.
- Their only state difference is the completion-to-fit coefficient (`1` versus `0`).
- Arm 3I outputs contain no forbidden temporal vocabulary.
- The relation schema contains no free-text statement or recommendation field.
- Requirement-artifact packets make no LLM call and receive exactly one deterministic `compatible`/`incompatible`/`insufficient` judgment per exact task clause; clause coverage, exact-span grounding, quoted/unquoted method fields, parenthetical quarantine, z-score/mean-plus-SD equivalence, incompatibility precedence, and the unknown/no-method insufficient rule are tested.
- No Arm-3 output contains recommendation or action language.
- No LLM history, DAG-neighbor, or arbitrary cross-task artifact packet is constructed.
- Batching preserves the complete packet multiset exactly once and uses only the two frozen groupings in §4.2.
- Each batch response returns exactly one result per packet fingerprint; missing, extra, duplicate, and cross-packet grounds invalidate or reject deterministically.
- Every profile-scope result contains exactly one grounded three-way judgment; an empty profile result invalidates the batch rather than silently deleting the declared prior.
- The fixed legend is byte-identical across variants and every rendered term matches §6.
- Only activated unique scopes are rendered, with stable scope and worker ordering.

### Updater tests

- Declared profile prior initializes each grounded worker/task scope at `+0.5` and remains unchanged without fit-bearing evidence.

- Completion changes task fit only in Arm 3I-noQ.
- Threshold crossings alter rendering only and never manager actions directly.
- Uniform-polarity replays document when 3I-Q and 3T are category-equivalent.
- A support-then-contradiction replay must discriminate the temporal arm:

3T:   after support B=+1.5; after contradiction B=0 → uncertain
```

- A contradiction-then-support replay must move 3T from `−0.5 contradicted` to `+1.0 supported`, versus `+0.5 supported` for 3I-Q. The command is fully local:

```

### Failure and tracing tests

- Generation/truncation/schema failure marks `invalidates_arm=true` and produces no fallback relation.
- Every proposal, rejection, accepted relation, belief update, rendering, prompt/hash, and cache event is traceable.
- Saved manifests include extractor/updater versions, prompt/schema hashes, model, seed, parameters, and invalidation state.

### Measurement tests

- Frozen relation labels resolve on seed-101 saved traces before live evaluation.
- Shadow probes join only when context and protocol hashes match.
- The audit reports fact recall, relation recall, correction opportunities, routing, and prompt sizes together.
- Arm 2-PAD matches the declared byte/token tolerance at B, C, mean, and late/max contexts.

## 12. Scope exclusions

Arm 3 does not:

- train or fine-tune the manager;
- purchase new observations through active probing;
- diagnose the hidden perturbation or name a private capability swap;
- recommend or enforce orchestration actions;
- use grader truth to evaluate artifacts online;
- establish broad generality from the primary toolset workflow alone.

Active probing remains Phase 3. Learned relation or belief modules remain later ML extensions after the training-free estimator is characterized.
