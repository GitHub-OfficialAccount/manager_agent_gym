# Changes to the core codebase

Deviations from upstream in `/manager_agent_gym`, with rationale. Kept
intentionally small — see OVERVIEW.md/CLAUDE.md for why the change was
needed; only entries that touch shared plumbing (not experiment-local code)
go here.

Entries marked **UPSTREAM LIMITATION** are *not* deviations of ours — they are
upstream behaviours worth knowing before assuming the implementation matches
the `ManagerAgent.pdf` specification. They are recorded here because this is
the file people check before making that assumption.

## 2026-07-28 — `description_override` on worker disclosures

**What changed:** `WorkerObservationDisclosure` gains `description_override: str | None`,
stored and applied by `ObservationPolicy` exactly as `capability_override` already was —
`_description_overrides` keyed by agent, applied in `redact_agent_config` as
`agent_description`. `None` leaves the canonical description untouched, so every existing
policy is unaffected.

**Why:** `agent_description` is a **second capability-bearing field** the manager routes on,
and revising capabilities alone left it stale. Observed directly: with
`portfolio_analyst`'s capabilities revised to `Methods: mean-plus-two-SD screening`, the
manager assigned it a robust audit anyway, reasoning *"portfolio_analyst **who handles
income/loan-amount portfolio audits**"* — quoting the unrevised description. Because a
robust audit *is* a portfolio audit, the stale description kept asserting fit regardless of
the capability list.

That made the capability intervention incomplete. `DISCLOSURE_PROFILES` carries
`current_description`, and application is gated on a new `revise_description` flag on the
**condition** — not on the `current` projection.

**Corrected within the hour, and the correction is the point.** Gating on the projection
silently changed what `full` and `silent_declared` mean: **13 `full` runs and 3
`silent_declared` runs already existed, generated with the canonical description.** Same
condition name, different intervention, is the provenance failure this project has logged
repeatedly. Worse, **the three `silent_declared` runs are the matched one-variable baseline
the gate-mechanism test needs** — revising them retroactively would have destroyed it. The
completed intervention is therefore its own condition, `silent_declared_both`, and every
pre-existing condition is byte-identical to what its runs were generated with.

**Note on the finding this qualifies:** `silent_declared` produced first-assignment routing
of 3/3 to the correct worker against `silent`'s 0/37 **with only half the capability surface
revised.** The incompleteness weakens the intervention, not the result.

## 2026-07-27 — `Inspect(Ti)` returns resource IDs, never content

**UPSTREAM LIMITATION plus one small deviation of ours.**

`ManagerAgent.pdf` §3.3 defines `Inspect(Ti)` as an observability-increasing
action — *"to view execution logs and outputs"* — and §3.4 makes the manager
artifact-blind by default (*"may not directly observe … the contents of
artifacts or detailed worker logs"*). So in the formalism, Inspect **is** how
the manager is supposed to see outputs.

`InspectTaskAction` is unchanged from upstream (`3f7a5d4`; verified by
Research-Engineer — zero diff lines touch it). It returns
`Inspected task {id} details: {task.pretty_print()}`, and
`Task.pretty_print` (`schemas/core/tasks.py:198`) emits

```
Output resources: ['<uuid>', '<uuid>']
```

— **identifiers only.** So the action bearing Inspect's name does not do what
the specification says Inspect does.

**The sharper point: the content renderer already exists and is never reached.**
`Resource.pretty_print(max_preview_chars=5000)`
(`schemas/core/resources.py:44`) renders a full content preview — stats, up to
5000 chars, up to 60 lines. `Task.pretty_print` cannot call it, because a
`Task` holds `output_resource_ids`, not `Resource` objects. **This is a wiring
gap one lookup wide, not a missing capability** — `InspectTaskAction` has the
workflow in scope and could resolve IDs → resources → `pretty_print()`.

**Our deviation, six lines, same file:** `Task.pretty_print` surfaces
`execution_notes` on `FAILED` tasks (`tasks.py:217-222`), with the comment
*"Surface why it failed — inspectors can't diagnose from status alone."*

> **We stated the general principle and applied it to exactly one branch.** The
> completed-but-wrong branch — the one that matters for competence change — was
> left as IDs. Recorded in `experiments/worker_replacement/METHODOLOGY_FINDINGS.md` §6c.

**Why it matters to the experiment:** at `q` t=20 the manager chose
`inspect_task` over rerouting — it reached for precisely the affordance §3.4
designates for an artifact-blind manager, and got a pointer. See
`experiments/worker_replacement/REFLECTION.md` §7 (the carrying gap) and §8 (why it is the
operative one). **Not yet fixed**; recorded so that a
decision to fix it is deliberate.

## 2026-07-25 — Serving-backend attribution on the native structured path

**What changed:** `core/common/llm_interface.py` now records which backend
actually answered each structured call, and in what cache state.
`_get_openai_client` builds the `AsyncOpenAI` client with an explicit
`httpx.AsyncClient` carrying a single `response` event hook; the hook reads
`provider`, `model`, `id`, `usage.prompt_tokens` and
`usage.prompt_tokens_details.cached_tokens` from the response body into a
`ContextVar`, and `generate_structured_response` attaches them to the existing
`structured_llm_response` run event as `serving_backend`. Applies to every
structured call — manager, judge, and belief alike — not just the belief role.

`cached_tokens` is recorded for the same reason as `provider`: prefix-cache
state is provenance that can change a temperature-0 verdict. Measured on the
relation-extraction path, cache-warm calls returned `supports_fit` in 45 of 46
samples where cache-cold calls did not, and a semantically null random prefix
moved one judgment from 1/20 to 8/20. Cache-hit probability also rises across
an episode as near-identical prompts accumulate, so the run record needs it to
be interpretable after the fact.

**Observability only.** The wire request is unchanged: the hook reads a
response, and the request body and headers were verified byte-identical with
and without the custom `http_client`. The hook swallows all exceptions, so
attribution can never fail a call. Nothing selects, pins, or reorders
providers.

**Why:** OpenRouter load-balances one model route (`openrouter/<provider>/
<model>`) across ~20 serving backends at quantizations from fp4 to fp8, and
picks per request. Measured on `deepseek/deepseek-v4-flash`, byte-identical
temperature-0 relation-extraction calls landed on DeepInfra, Ionstream,
Venice, and AtlasCloud within a single probe, and the answering backend
shifted the returned stance distribution. Worse, `seed` is absent from
`supported_parameters` for several of those backends (Baidu, StreamLake,
SiliconFlow, Venice, Fireworks, DigitalOcean, DeepSeek), so a seed we send is
silently ignored there with no error. Which backend answered is therefore
provenance that can change an output, and it belongs in the run record for the
reproducibility statement rather than being unobservable. Previously the run
trace recorded the model route we asked for and nothing about what served it.

## 2026-07-24 — Belief-layer model role (`"belief"`)

**What changed:** `ModelRole` in `core/common/model_provider.py` gains a
fifth role, `"belief"`, resolved via `get_model_for_role("belief")` from a
new `Settings.BELIEF_MODEL_NAME` (`config.py`), following the exact pattern
of `manager`/`worker`/`stakeholder`/`judge`. `Arm3IObservationAid` (Arm 3's
live observation-aid builder) now takes an explicit `belief_model` parameter
distinct from its existing `model` parameter — `model` continues to serve
the (deterministic, LLM-free) Arm-2 ledger builder only; `belief_model` is
what actually gets passed to `Arm3SemanticExtractor`, defaulting to
`get_model_for_role("belief")` when not explicitly supplied. `run.py` and
`arm3_replay.py` both gained a way to override it (`--belief-model` /
`--model`, respectively) independent of the manager's model, and it is now
recorded in every Arm-3 run's `observation_aid_diagnostics` and manifest.

**Why:** the DS-REROUTE Arm-3 belief-layer comparator generalization
(`COMPARATOR_GENERALIZATION.md`) explicitly defers the belief-layer model
choice to the human researcher, to be picked empirically via a bake-off
against the offline gates — and requires it not be hard-wired to the
manager's model. Previously `Arm3IObservationAid` was constructed with
`model=manager.model_name` at its one live call site, silently coupling the
belief layer's model to whatever the manager happened to be running. Adding
a same-shaped fifth role keeps this consistent with the codebase's existing
per-role routing convention rather than inventing a parallel mechanism.

## 2026-07-23 — Lossless task-bundle observation-aid rendering

**What changed:** the existing Arm-2 atomic ledger remains append-only and
unchanged for storage, recall audits, snapshots, and Arm-3 relation grounding.
Its manager-facing renderer now groups atoms deterministically by attributed
worker/task and source pointer while retaining every evidence ID, first-seen
timestep, source pointer, and verbatim fact. Arm 2 and all Arm-3 selectors use
the same rendered prefix. Renderer version and specification hash are reported
in diagnostics.

**Why:** repeating full worker/task/source metadata on every atomic line made
the manager reconstruct obvious task-level units and inflated the relevant
seed-101 prefix by 34.1%. The projection is exactly reversible and performs no
selection, summarization, comparison, inference, or reweighting, so it improves
presentation without changing the evidence boundary or Arm-2/Arm-3 contrast.

## 2026-07-21 — Explicit Arm-3 observation-aid selectors

**What changed:** `ObservationAidMode` and the structured manager's existing
builder-dispatch branch now recognize `arm3i_noq`, `arm3i_q`, and `arm3t`. The modes use
the same `ObservationAidBuilder` interface and the same pre-action observation
capture path as Arm 1/2. All extraction, belief assembly, rendering, caching,
and persistence remain experiment-local under `experiments/worker_replacement/`.

**Why:** labeling an Arm-3 builder as `atomic_evidence_ledger` would make the
serialized observation policy disagree with the actual manager treatment.
Explicit names preserve declarative condition manifests, isolate the
completion-to-fit coefficient (`1` in noQ, `0` in Q/T), and distinguish the
frozen temporal updater from the no-decay Q state. Defaults and existing aid
modes are unchanged.

## 2026-07-17 — Exact pre-action observations and observation-aid channel

**What changed:** the manager now retains the `ManagerObservation` constructed
for each decision. Timestep results, traces, and callbacks reuse that pre-action
snapshot instead of reconstructing an observation after manager-action and
worker execution. `ManagerObservation` also has an optional `observation_aid`,
selected declaratively by `ObservationPolicy`; the structured manager invokes a
separately configured builder only when the policy selects `generic_summary`.

**Why:** the former callback observation was post-transition and therefore
closer to the next timestep's observation than to the observation that produced
the recorded action. That made detection timing ambiguous, especially at a
scheduled change boundary. Exact pre-action capture aligns stated and behavioral
detection with the same `o_t`. The separate aid channel supports Phase 2 while
keeping the native `none` arm free of summarizer calls.

**Arm-1 reliability follow-up (2026-07-18):** removed the summarizer's fixed
500-token completion cap after a real DeepSeek V4 Flash smoke test spent 304
tokens reasoning and truncated otherwise valid summary JSON. The 250-word prose
contract remains. A summary inference failure now produces no aid for that
timestep and emits a traced `observation_aid_failed` event marked
`invalidates_arm=true`, rather than aborting the workflow; failures are not
cached.

**Arm-2 hardening (2026-07-18):** replaced the preliminary LLM selector with a
versioned deterministic enumerator. It appends every declared worker-resource,
task-outcome, and worker-message candidate; covers full workflow-summary changes;
has no ranking/cap; and traces its specification hash, complete candidates,
duplicates, and zero omissions. The schema remains dimension-free and contains
no expected-method comparison, competence/change label, inferred absence, or
recommendation. Added `append_only_summary_log` as a persistence-only control.

## 2026-07-15 — Scheduled manager-facing observation disclosures

**What changed:** `ObservationPolicy` now accepts scheduled worker disclosures
that can overlay a worker's manager-visible capability declaration and emit an
optional announcement. The execution engine applies these disclosures after
the registry applies objective worker mutations at the same timestep. The
overlay is private observation-policy state: it never mutates the worker config,
tools, prompt, or model. Disclosures are serialized in the policy manifest and
are idempotent per timestep.

**Why:** DS-REROUTE previously encoded silent/partial/full observability by
changing `ToolSwap.new_agent_capabilities` and `announce`. That coupled the
objective perturbation to its manager-visible projection, weakening the claim
that conditions differ only in observation. The experiment now registers an
identical canonical worker mutation in every non-control condition and composes
it with a separate `ObservabilityDefinition`.

## 2026-07-15 — Strategy-neutral non-stationarity prior for managers

**What changed:** the shared structured-manager system prompt now notes that
agent characteristics and behavior may evolve, asks the manager to use current
observations and outcomes, and permits revisiting earlier assumptions while
balancing quality, throughput, and recovery cost.

**Why:** in a fully observed teammate-change run, the manager correctly stated
the worker's updated method and then contradicted that observation in the same
assignment decision. The new prior does not reveal whether, when, or how a
worker changes, prescribe capability matching, name a recovery action, or
alter the manager's action space. It only removes the implicit stationary-team
assumption across all conditions.

## 2026-07-14 — Optional declared-capability update on tool swaps

**What changed:** `ToolSwap` and the registry's scheduled replacement path now
accept an optional `new_agent_capabilities` list. When supplied, the worker's
manager-visible declared capabilities are replaced atomically with its task
tools; when omitted, the existing declaration is preserved exactly.

**Why:** a fully signaled tool change previously replaced the real tools while
repeating the worker's original capability declaration in every manager system
prompt. That contradicted the explicit change announcement and caused manager
beliefs to revert across turns. Keeping the metadata update optional preserves
silent conditions: they continue exposing only the original prior declaration
plus ordinary behavioral evidence.

**Current DS-REROUTE use:** observability was decoupled on 2026-07-15. Its
objective tool swap now always writes the same canonical post-change
capabilities, while `ObservationPolicy` independently preserves or changes the
manager-facing declaration. The optional registry field remains available to
other experiments and for canonical capability updates.

## 2026-07-14 — Native failed-task retry action

**What changed:** added `retry_task` to the manager's native action set. It
reopens a failed atomic task under the same ID, preserving its dependency edges,
instructions, and failure notes while resetting attempt-specific status, timing,
cost, quality, and output references. The action may optionally select a new
agent in the same mutation. The execution engine removes a successfully reopened
task from its current failed-task set before native readiness and scheduling run.

**Why:** creating a replacement task for a transient execution failure changes
the node ID and requires several dependency mutations before downstream work can
resume. That made a basic retry consume most of a finite episode and allowed a
completed replacement to remain disconnected. Retrying the existing node is a
narrow orchestration operation; it does not edit, repair, or replace a worker,
and the action remains identical across all experimental conditions.

## 2026-07-12 — Trimmed `Resource`'s docstring (manager_agent_gym/manager_agent_gym/schemas/core/resources.py)

**What changed:** removed the fenced ` ```python ... ``` ` worked example from
`Resource`'s class docstring. No field names, types, defaults, or
`description=`/`examples=` kwargs were touched — purely the class-level
docstring prose.

**Why:** `AIAgent` (`core/workflow_agents/ai_agent.py:83`) forces every worker's
final answer to validate against `output_type=AITaskOutput`, which nests
`Resource` via Pydantic's auto-generated JSON schema
(`AITaskOutput.model_json_schema()`). That schema embeds a model's docstring
verbatim as the JSON Schema `"description"` field — so `Resource`'s old
docstring, code example and all, was sent to the model on *every single tool
call*, as part of the tool-call/structured-output request.

Root-caused via a controlled A/B (see the AHT session that found this):
with a model prone to markdown-fence formatting quirks (`deepseek-v4-flash`
via OpenRouter), embedding a real ` ``` ` fenced code block inside the
required-output schema measurably primed the model to (a) sometimes skip
calling the actual tool and fabricate a plausible answer instead, and (b)
occasionally call the wrong tool. Isolated by testing bit-for-bit identical
prompts/tools/schema-structure, varying only whether this docstring's prose
was present:

- Full schema (with fenced example): ~50% of calls skipped the tool entirely
  (6/11 across two raw-litellm batches).
- Structurally-identical schema with all docstrings/examples stripped: 0/8
  skips.
- Real `AIAgent.execute_task()` path, same worker/model, only this docstring
  edited (no other prompt/schema changes): 8/8 correct tool calls (up from
  the ~50% baseline measured before the edit).

**What this does NOT fix:** `deepseek-v4-flash` on OpenRouter still
intermittently wraps its final structured JSON answer in markdown code
fences even with this fix (~7/8 crash rate observed in one batch, on top of
the underlying tool-call now working) — a separate, pre-existing model
quirk, mitigated (not eliminated) by prompt-level "no markdown fences"
hardening in each experiment's own worker prompt. Not addressed by this
change.

**Safety check performed:** grepped the codebase for anything depending on
the removed example text (`"Stakeholder Brief v1"`, `"Two-page summary for
exec review"`) — only the docstring itself referenced it; no tests or other
code paths depend on the exact docstring content.

## 2026-07-13 — Plain-text output for OpenRouter workers (manager_agent_gym/manager_agent_gym/core/workflow_agents/ai_agent.py)

**What changed:** for `openrouter/`-prefixed worker models, `AIAgent` no
longer passes `output_type=AITaskOutput` to the Agents SDK. Instead it (a)
appends `PLAIN_TEXT_OUTPUT_CONTRACT` (a prompt-level statement of the
AITaskOutput JSON schema) to the worker's system prompt, and (b) parses the
model's plain-text final reply back into `AITaskOutput` via
`_parse_plain_text_output` — a lenient, never-raising parser that tolerates
markdown fences, surrounding prose, drifted key names
(`generated_resources`/`output_resources` → `resources`), and scalar/list
mismatches, falling back to wrapping the raw reply verbatim in a single
resource so the worker always produces output. Non-OpenRouter models are
untouched (`output_type=AITaskOutput` exactly as upstream).

**Why — the actual root cause of weeks of "unreliable worker" symptoms:**
`output_type` makes the SDK send a strict `response_format: json_schema` on
**every** request, including turn 1 where a tool call is expected. Most
OpenRouter backends grammar-enforce that schema during decoding, which makes
emitting a `tool_calls` message *literally impossible* — the model is forced
to fabricate a plausible final answer without ever running the tool.
Measured with byte-identical request bodies via raw HTTP (no litellm/SDK
involved), provider pinned per request:

- WITH `response_format`: **0/9** tool calls across DeepInfra, Parasail,
  AkashML, AtlasCloud, StreamLake, Alibaba (all fabricate valid-schema JSON).
- WITHOUT `response_format`, same body otherwise: **12/12** tool calls,
  including on StreamLake and Alibaba.
- End-to-end through the fixed `AIAgent` path (deepseek-v4-flash, default
  routing, no retries): **16/16** success, 16/16 tool calls, 16/16 parseable
  answers across a 2-tier × 4-column × 2-rep sweep.

**This supersedes the earlier "bad provider" theory** (StreamLake blocklist,
briefly wired as `ModelSettings(extra_body={"provider": {"ignore":
["StreamLake"]}})` — now removed). There was never a bad provider: Baidu was
simply the one backend that does *not* hard-enforce `response_format`, so
tool-calling worked there — and, for the same reason, unconstrained decoding
there could emit markdown-fenced JSON, which is exactly the intermittent
fence-crash previously blamed on the model. When Baidu became rate-limited
upstream (2026-07-13, observed 429s), traffic spilled to grammar-enforcing
backends and the whole substrate collapsed — which is what exposed the real
mechanism. Both long-standing failure modes (silent tool-skip fabrication
AND fenced-JSON crashes) trace to this single `response_format`-vs-tools
conflict, and both are eliminated by this change.

**Trade-off:** OpenRouter workers lose provider-side schema *enforcement*;
the schema is prompt-specified and parsing is lenient. In the 16/16 sweep the
model followed the contract fine (occasional fences/key drift, all absorbed
by the parser), and the never-raising fallback preserves the "a worker always
outputs something" experiment invariant.

**Follow-up hardening (2026-07-13):** a full 32-task paired environment gate
found two otherwise successful model replies whose resource object omitted or
blanked its `content` field. The parser had accepted those objects, allowing a
native task to be marked completed with an empty artifact. Blank-content
objects are now discarded; if no substantive resource remains, the existing
fallback preserves the complete raw reply as resource content. This does not
change model routing, LiteLLM, tool availability, or valid structured replies.

## 2026-07-13 — Configurable AI-worker turn limit and concise task prompt

**What changed:** `AIAgentConfig` now accepts an optional `max_turns`. When it
is unset, `Runner.run` receives no override and retains the Agents SDK default;
experiments can opt into a larger limit without changing other workers. The
generic AI task template also no longer requests an extra 0–5 quality score or
duplicates the structured-output field list. It asks for appropriate resources,
a brief rationale, confidence, and relevant notes while explicitly preserving
reasonable verification and free tool choice.

**Why:** the `worker_replacement` calibration probe normally required 4–9 model turns.
With the SDK default of 10, one of 13 isolated runs exhausted the limit after
continued verification, and another valid run finalized on turn 10. With the
same prompt and `max_turns=15`, 10/10 isolated runs completed in 4–9 turns with
no empty replies. The experiment sets 15; all existing configurations retain
the upstream default. The prompt cleanup removes an inconsistency: it requested
a quality score that is not part of `AITaskOutput`.

**Empty-final-response recovery:** the same probe also reproduced a distinct
provider/model outcome: a successful tool turn followed by a model response
containing no output items, which the SDK treated as a blank final string. For
OpenRouter workers only, `AIAgent` now makes one continuation using the complete
existing run history and asks a tool-free clone of the same agent to serialize
the final result in the existing output format. The normal run retains every
configured tool; only this post-completion fallback hides tools so it cannot
restart the task or enter a second tool loop. Context, model, Agents SDK, and
LiteLLM routing are unchanged. A second blank response fails the task instead
of creating an empty completed artifact. Both calls' costs are retained. A
fresh fixed-assignment pair subsequently passed all gate checks with 16/16
nonempty completions in both arms.

**Task-prompt follow-up (2026-07-14):** removed the generic phrases
`including reasonable verification` and `once you are satisfied with the
evidence`. They encouraged open-ended verification even when an
experiment-specific system prompt and deterministic tool description said a
complete result was already sufficient. The shared template still leaves tool
choice free; it now neutrally asks workers to use tools when useful and return
the requested result. The `worker_replacement` experiment independently raises its
safety ceiling to 30 turns while this behavior is measured.

## 2026-07-14 — Optional offline run tracing

**What changed:** added an opt-in `RunTraceRecorder` that accumulates ordered,
JSON-safe events in memory and writes a single bundle after an episode. The
common structured-LLM boundary records exact messages, response schemas, parsed
responses, and failures while tracing is active. `AIAgent` additionally records
its effective instructions, generated task prompt, resources, configured tools,
SDK model/tool history, raw responses, parsed deliverable, errors, and the
one-time blank-output recovery path. With no active recorder, execution and
output behavior are unchanged.

**Why:** native timestep JSON already contains workflow snapshots, observations,
actions, messages, resources, and transitions, but exact prompts and SDK worker
histories were discarded after each call. The data-science experiment needs a
complete local, read-only run viewer. Capturing only those ephemeral values and
bulk-composing them with native timestep results avoids a database, real-time
telemetry service, or a parallel execution model.

## 2026-07-27 — Fail loudly when no manager turn succeeds

**What changed:** `experiments/worker_replacement/run.py` now raises `RunTotallyFailed`
after writing artifacts if a run produced at least one manager action and **none
of them succeeded**, and drops an `INVALID_RUN.json` marker in the run directory
recording the turn count, `r_check`, and the distinct action errors. Artifacts are
written first and deliberately left in place: they are the diagnostic evidence.
Runs with any successful turn are unaffected, so no existing cell changes
behaviour and no configuration hash moves.

**Why:** a run whose every manager turn is `failed_action` previously exited **0**
and wrote a complete-looking directory with `r_check=0.000`. Observed 2026-07-27:
a missing dependency group made all 32 turns fail and the process reported
success. Two failure modes compound. A totally failed run is indistinguishable
from a successful one to anything checking exit status; and its all-zeros
artifacts land in `experiments/worker_replacement/outputs/`, which every analysis sweep
globs. One such run silently corrupts the `r_check` spread, per-run rate
denominators, and any contradicted-cell sweep, with nothing to notice — the
defect was caught only by reading the score. The `INVALID_RUN.json` marker lets a
sweep skip the directory structurally rather than inferring breakage from a
suspicious number.

**Scope note:** this is a guard on an experiment entry point, not on the shared
engine. It changes exit status and adds a file; it sends nothing new to any model.

## 2026-07-27 — Record every action's result, not only successful ones

**What changed:** `WorkflowExecutionEngine` now writes the returned `ActionResult`'s
`success` and `summary` back onto the manager action before logging it, for all
action types and all outcomes.

**Why:** each action's `execute()` set `self.success = True` and
`self.result_summary = summary` on its **success path only**. Every early return —
task not found, wrong status, unknown agent — returned a populated `ActionResult`
but left the action's own fields `None`. The manager still saw the refusal in its
action history, so behaviour was unaffected; but `manager_actions.json`, which most
analyses read, recorded `"success": null, "result_summary": null` and a refusal was
indistinguishable from an action that did nothing.

Observed 2026-07-27 in `amendment_fav`: at t=11 the manager correctly diagnosed a
wrong-method artifact and issued `retry_task` naming a replacement worker. The
harness refused it correctly — *"has status completed; only failed tasks can be
retried"* — and that text reached the manager at t=12 and every later timestep. The
run artifact showed only `null`. Reading `manager_actions.json` alone, refusal and
silence were the same observation, and the first analysis of that run drew the wrong
inference before `events` was consulted.

**Scope:** recording only. No behaviour changes, no action semantics change, no
configuration hash moves. Fixed centrally in the engine rather than in each action's
failure branches, so it covers every action type and every early return rather than
the ones someone remembered to patch.

## 2026-07-29 — RefineTaskAction logged "updated from X to X"

**What changed:** `RefineTaskAction.execute` now captures the previous value
before assigning, for `description`, `estimated_duration_hours` and
`estimated_cost`. A regression test (`experiments/worker_replacement/test_no_mutate_then_log.py`)
fails the build if any log line in `manager_agent_gym/` interpolates an attribute
the same block already overwrote.

**Why:** the assignment preceded the log, so both sides of "updated from {old} to
{new}" interpolated the *same* value. The record read "updated from X to X" and
**the pre-refinement value was destroyed at source** — not recoverable from the
action log, only from per-timestep task snapshots if retained. Any measurement of
specification effort is a delta, so this removed the "before" side of every such
measurement. No published claim depended on it; found during an action-space
enumeration.

The correct idiom already existed twenty lines below, in the same function:
`additional_instructions` captures `old_instruction` before overwriting. This was
an idiom applied unevenly rather than a missing one, which is why the fix ships
with a mechanical check rather than three edits.

**Scope:** upstream code, three log strings and one test. No behaviour changes —
the task mutations were always correct; only the record of them was wrong. No
configuration hash moves.
